01

Infrastructure

The four backing services Nodyra expects in production, and the compute the sandbox needs. Get these wrong and the failures show up later as data loss rather than as errors.

Who: whoever owns the cluster and the cloud account

SQLite is the default and it is a development default. With RUNTIME_MODE=production Nodyra emits a startup warning for it, because a single-writer file database cannot serve concurrent workers durably. Point DATABASE_URL at Postgres before anything else — migrating later means moving encrypted credentials.

DATABASE_URL=postgresql+asyncpg://nodyra:...@pg.internal:5432/nodyra

Without a shared queue backend, every API replica keeps its own in-process queue: runs are invisible to other replicas and are lost on restart. Nodyra treats this as replica-unsafe and says so at startup. Redis is also what makes rate limiting atomic across replicas.

Local artifact storage is per-pod: a run’s output lands on one worker’s disk and disappears when it restarts. Set artifact_storage_backend=s3 and artifact_s3_bucket — setting the first without the second makes every upload fail, which Nodyra warns about separately.

Every tier is allowed to sandbox — it is a Community entitlement — but the runtime setting ships as off. With it off, workflow Code nodes run arbitrary Python in the worker process, on the host. That is defensible only when the people writing workflows are the people who already own the machine. Enabling multi-tenancy auto-promotes it to required; a single-tenant deployment stays off until you say otherwise, so set EXECUTION_SANDBOX=required yourself. Nodyra then prefers kata, then gVisor (runsc), then runc — on shared hardware, prefer one of the first two. Readiness only inspects the runtime when the sandbox is not off, so a green /health/ready proves nothing about isolation if you left it at the default.

Single process (dispatch_role=inline) is fine for one team. Splitting API from workers turns /internal/* into a network surface, which is why INTERNAL_API_TOKEN becomes a hard startup requirement the moment you leave inline. Keep webhook_role=ingress (the default) so a webhook burst cannot starve the editor.

The database holds every encrypted credential and every workflow. A backup you have never restored is a hypothesis. Do the restore drill once now, into a scratch database, and note how long it took — that number is your real RTO.

02

Security

Nodyra fails closed on the three settings that would otherwise be catastrophic rather than merely degraded. The rest of this list is the posture work that no startup check can do for you.

Who: whoever would be answering the questions after an incident

This one key signs session tokens and derives the master KEK for the credential vault. Left at the built-in default with auth enabled, anyone can forge a session for any user and decrypt every stored credential. Nodyra aborts startup rather than let this ship.

python -c "import secrets; print(secrets.token_urlsafe(48))"

Nodyra sends Access-Control-Allow-Credentials: true. Paired with a wildcard origin that would let any site drive authenticated cross-origin requests — and browsers reject the combination anyway, so it is never a working configuration, only a footgun. Startup refuses it.

Blank, with dispatch_role anything but inline, means /internal/* accepts unauthenticated worker-level calls. Startup refuses this too. Use a distinct high-entropy secret — not the same value as SECRET_KEY.

This single flag disables every check above. It exists for a throwaway local instance. If it is set in a production manifest, the three gates before this one are decorative. Grep your manifests for it before every release, not just the first.

grep -RIn "RUNTIME_ALLOW_INSECURE" deploy/ k8s/ .env*

Credentials use envelope encryption: a per-credential data key, wrapped by a per-organisation key, wrapped by a master key. Pointing kms_provider at Vault, AWS or GCP moves that master key out of Nodyra’s reach entirely. Each provider has its own required fields and startup validates them. If you choose Vault, use https:// — the plaintext KEK crosses that connection, and Nodyra refuses http:// to a non-loopback host unless you explicitly opt in.

Workflows make HTTP requests on the operator’s behalf, so every user-supplied URL is a potential SSRF. Nodyra resolves DNS on each call and refuses private, loopback and link-local targets — which also closes DNS rebinding and cloud metadata. A single-tenant deployment that legitimately calls internal services opts back in with NODYRA_ALLOW_PRIVATE_EGRESS=1. Never set this on a multi-tenant instance.

SAML 2.0 and OIDC both ship. Turning on SSO without closing the local password path just adds a door; it does not replace one. Also set auth_registration_role deliberately — it defaults to viewer, which is the safe choice, and is worth confirming rather than assuming.

Session tokens travel in every request. Terminate at your ingress or load balancer and make sure the plain-HTTP listener is not reachable from outside the cluster.

03

Application

Schema, licence, and the first humans. This is the part that has an ordering constraint: migrations run as a separate job, and readiness deliberately fails until they have.

Who: whoever owns the Nodyra instance itself

96 migrations, run by a job separate from the pods. Readiness compares the database’s alembic_version against the head baked into the image, so a lagging or failed migration job keeps pods out of the load balancer instead of letting them serve 500s on every write. That check is the safety net — do not disable it.

cd apps/api && alembic upgrade head

Set NODYRA_LICENSE_KEY, or store it in system settings — the environment variable wins. Verification is a signature check done entirely offline: no phone-home, air-gap friendly. Leave it blank and you get Community, which is a working product, not a crippled one.

Four roles, ranked: viewer (10), editor (20), admin (30), owner (40). Owner is a break-glass account. Give yourself a separate admin for ordinary work so that the audit trail distinguishes routine changes from privileged ones.

Environments are built fresh from your declared packages and are the unit that credentials are scoped to. Build them before the first real run, not during it — a first build is slow and you do not want to discover that during a demo.

Community allows one runner, Pro five, Enterprise unlimited. A registered runner that never checks in looks identical to a healthy idle one until you try to run something.

04

Release & verification

The evidence step. Everything above is a claim about the deployment; this is where you find out whether the claim is true.

Who: whoever is going to say “it is live”

/health/live answers “the process is up”. /health/ready answers the question you actually care about: database reachable and at the expected schema revision; Redis reachable when it backs the queue; sandbox runtime available on any process that owns local execution. Each is skipped when genuinely not a dependency, so a green ready means something.

python scripts/wait_for_ready.py --url https://nodyra.example.com/health/ready

What good looks like

HTTP 200 with every configured check reporting ok. A 503 naming database with two revision ids is the migration job lagging — go back to 03, do not restart pods hoping it clears.

This is the single most useful endpoint in the product at deploy time. It reports the advisory problems that are not severe enough to abort startup but will cost you later: SQLite in production, local artifact storage, no shared queue, inline webhooks, a wildcard CORS origin, a default secret. An empty warning list is the actual go-live signal.

curl -s https://nodyra.example.com/ops/runtime-mode | jq .

Not a health check — a workflow that uses a credential, runs in the sandbox, and writes an artifact. That single run exercises the vault, the queue, the runtime and object storage together. Then restart a worker mid-run and confirm the run recovers rather than hanging.

The drill from 01, done against the real production backup this time. Confirm the restored instance can decrypt a credential — that proves you backed up the key material, not just the rows. This is the check that most deployments skip and most incidents need.

Which image tag do you go back to, and does that tag’s schema still work against the migrated database? Migrations are frequently one-way. If the answer is “restore from backup”, say so explicitly now rather than discovering it at 2am.

05

Day 2

What has to keep being true after launch day. These are recurring, not one-off.

Who: whoever is on call

Page on /health/ready failing. Graph /ops/queue — a queue that climbs monotonically means workers are dead or wedged, and it shows there long before users notice. /ops/drain is what you use to take a worker out cleanly.

The log is append-only in the application — nothing in the product updates an audit row — but a retention window does remove old entries, and the database is not append-only at the storage layer. Stream /audit/export.ndjson into your SIEM or object storage on a schedule so the record outlives both.

Retention deletes audit events older than the cutoff. Choose it against your compliance obligation rather than leaving the default and finding out what it was during an investigation.

Run it once now while nothing is wrong, so that the first time you use it is not during an incident — and so you know what it contains before you send it to anyone.

python scripts/generate_support_bundle.py

Nodyra executes user-supplied Python. That raises the cost of being slow to patch, both the platform and the images your environments build from.

Watches RSS, file descriptors and thread count over a sustained run and reports a gauge that climbs and does not come back down. Warm the process first — a cold start fills pools, and rising numbers during that fill are not a leak.

python scripts/endurance_test.py
