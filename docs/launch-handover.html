What’s left before Nodyra launches

Twelve commits, four production bugs found by running the software rather than testing it, and one honest answer about the score.

8.5/10 Where it actually stands

No, Nodyra is not 10/10 — and the reason is specific rather than vague. Yesterday the code passed 9,811 tests, a full CI certification, and my own audit. Then I ran the deployment runbook against a real stack, and inside one afternoon that turned up four production bugs: every freshly built environment failed to start, and two of sixteen starter templates were broken, one of them silently.

Nothing was wrong with the tests. They ran against a locked dependency set and a SQLite database; the product runs against freshly resolved dependencies and PostgreSQL. The gap between those two worlds is where all four bugs lived.

That gap is now much narrower — templates are executed, not just parsed; contributors are told what SQLite hides; the suite passes on PostgreSQL. But a codebase earns a 10 by surviving contact with reality, and Nodyra has not yet had any: no production traffic, no external pentest, no live payment, and not one green CI run in a fortnight.

Bound the 72 unbounded dependencies engineering

This is the highest-leverage engineering work left, and it is the general form of the worst bug found this session.

packages/nodes declared mcp>=1.28.1 with no upper bound. Your lockfile pins 1.28.1, so the dev venv and CI never saw anything else — but a workflow environment resolves its dependencies fresh and got 2.1.1, which had removed a symbol the code imports. Result: import nodyra_nodes raised, the runtime never started, and every environment was broken while every test stayed green.

I fixed that import. There are 71 more declarations shaped exactly the same way — fastapi>=0.110, cryptography>=48.0.1, duckdb>=1.0, boto3>=1.34 and so on. Any of them can break every new environment on any day a maintainer cuts a major release. The fix is upper bounds plus a periodic resolve-fresh check in CI; it needs judgement per package, which is why I have not done it unilaterally.

Put one real charge through Stripe only you

The subscription system is built and its licence path is verified end to end — a signed key raises the tier, a tampered payload is refused, an expired key soft-downgrades rather than failing closed. What has never happened is a real transaction: no live Stripe account, no webhook delivered by Stripe itself, no card declined and recovered.

Do it in test mode first, then once for real with your own card, and cancel it. Until then the billing path is theory.

Commission an external pentest only you

Nodyra executes user-supplied Python and holds other people’s credentials. I closed a full audit this session — Argon2id, a login timing oracle, SAML entity expansion, credential-test SSRF, plaintext Vault transport, a WebSocket authorisation gap, archive path traversal — and added standing gates so those classes cannot recur.

But I audited my own work, which is worth less than an adversary doing it. docs/security-pentest-checklist.md is a good brief to hand a firm.

Run the endurance check for real only you

scripts/endurance_test.py defaults to sixty minutes and its own help says a leak needs hours to be visible. Three attempts were killed by session limits here, so I have no result and am reporting none rather than running eight minutes and calling it verified.

python scripts/endurance_test.py --duration-minutes 240

Run it against a production-like deployment and keep the report. The detector already distinguishes a warm-pool fill from a genuine leak.

The rollback plan is a decision to write down before you need it — migrations are frequently one-way, so if the honest answer is “restore from backup”, say so now. Alerting on readiness and queue depth needs your stack. A patch route inside a day is a commitment about your process. Runner hardware is machines I do not have.

For the recordWhat was actually settled

Verified against a live stack, not asserted

  • Backup and restore — pg_dump, restore into a scratch database, and a credential decrypted from the restore. The same restore with a different master key was refused, so the success was not a no-op. Measured RTO: 2.6s.
  • Readiness is not vacuous — 503 naming both revisions on a rolled-back schema, while /health/live stayed 200.
  • The licence path — a signed Pro key grants exactly observability, git sync and sandbox; a payload edited to say enterprise is refused; an expired key soft-downgrades. The same key is refused against the production public key, proving those were signature checks.
  • Go-live signal reached — /ops/runtime-mode returned "warnings": [] after configuring S3 storage and an internal token, rather than by ignoring them.
  • The support bundle redacts — checked directly against six real secrets, including the master key and session token. None appear.
  • The launch pages stopped lying — they were selling Pro customers audit-log export and RBAC that the code grants only to Enterprise, and advertising SCIM, which does not exist. 22 tests now fail the build if any claim drifts from TIER_DEFAULTS.
